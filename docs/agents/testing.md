# 验证清单

> scope: 所有端 ｜ 触发: 交付前/发布后验证 ｜ 复核: 2026-11-24

> 最后核对：2026-11-24。原则：**没在设备上看到效果，不算通过。**

## 1. 本地 harness（改脚本后必跑）

用真实的响应体跑脚本，不要自己编数据：

```bash
# 从 HAR 里取出目标接口的响应体
node scripts/mock-harness.js <script.js> <xxx.har> <url 子串>
```

脚本要能在 node 里直接跑，意味着它不能依赖客户端全局对象 —— 在文件末尾用一层适配：

```js
// 真机注入
if (typeof $response !== 'undefined') { main(); }
// 本地测试
else if (typeof module !== 'undefined') { module.exports = { transform }; }
```

## 2. 四个分支

| 分支 | 期望 |
|---|---|
| 正常 JSON、`errno=200` | 目标字段被改写，其余字段原样保留 |
| body 不是 JSON | 原样放行，不改 |
| `errno≠200` 或业务错误 | 原样放行，不改 |
| `data` 为空 / 类型不符 | 原样放行，不改 |

再额外确认：字段数「真实 vs 输出」一致（除故意新增的字段），样例值符合预期。

## 3. 设备验证

1. 脚本是否命中：Surge / Loon 的请求详情里能看到脚本名和耗时；没命中先查 pattern、MITM hostname，再查**这个接口这次操作到底有没有被调用**。
2. 页面是否真的变了：这一步只有用户能确认。没变化分两种：接口没被调用（补抓 HAR）／字段不对（看源码或继续探测，最多两轮）。
3. 多设备：模块的启用状态不跨设备同步，逐台开。

## 4. 发布校验

```bash
# 1) 每个 raw 链接必须 200
curl -s -o /dev/null -w '%{http_code}\n' '<raw-url>?v=1.8.0'

# 2) 内容是不是新版（绕缓存）
curl -s '<raw-url>?x=1' | head -5

# 3) 托管在 gist 时用 API 直接看内容，最可靠
gh api gists/<id> -q '.files["<file>"].content' | head -5
```

- GitHub raw 有传播延迟（实测 30 秒～2 分钟以上，偶发更久），发布脚本要轮询到内容更新为止，窗口给 2 分钟以上。
- 交付话术三段：改了什么 / 期待看到什么 / 还不对要什么材料。

## 5. 回归

每次改脚本，至少重跑一遍**上一版验证过的场景**，避免修 A 破 B。模块里有多条脚本时，逐条确认 pattern 没有互相抢。
